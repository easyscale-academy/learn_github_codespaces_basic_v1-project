# 收尾: 把这套工作流带走

## 1. 概览

到这里, 这门课的内容就全部讲完了.

前面每一篇解决的都是一个具体问题, 一篇一篇读下来, 你可能还没意识到它们合起来是什么. 这一篇不教新东西, 只做四件事: 把散落的知识点串成一条线, 说清楚云端环境在你整个学习路径里处于什么位置, 回答一个很实际的问题 (以后每次开始新任务, 你到底该在哪干活), 最后给两个还想往前走的方向.

---

## 2. 学习目标

技能这个东西有个特点: 学的时候是一块一块学的, 用的时候却是连成一片用的. 如果只记住了一块块的操作, 遇到真实场景时还是会卡, 因为真实场景不会告诉你现在该用哪一块.

所以收尾这一步不是走形式. 把学过的东西重新组织成一条你能从头讲到尾的主线, 它才算真正变成你的.

读完这篇, 你将能够:

1. 用一条完整的主线复述这门课教过的全部内容
2. 说出一次完整的日常开发循环包含哪些步骤, 以及它们的先后顺序
3. 判断云端开发环境在什么时候是最优解, 什么时候该换成本地环境
4. 面对一个新任务时, 根据手上的机器和活儿的性质, 选出该用哪套环境
5. 说出两个继续往前走的方向, 并知道从哪几个关键字开始查

## 5. 你会的其实是一条完整的主线

回头看, 这门课讲的其实是同一件事的三段.

| 这一段 | 解决的问题 | 哪几篇 | 走完之后你有了 |
| :--- | :--- | :--- | :--- |
| 有地方干活 | 环境这道门槛怎么绕过去 | 02, 03, 04 | 一个随时能开, 搞坏了也不心疼的开发环境 |
| 干完的活留得下来 | 改动怎么从临时状态变成项目历史 | 05, 06, 07 | 一套能安全留存, 也能和别人协作的流程 |
| 花的钱心里有数 | 这东西怎么计费, 怎么用才不浪费 | 08 | 对成本的基本掌控, 外加一道预算上限 |

中间那一段是这门课真正的重头, 值得多说一句: 05 教会你 commit 和 push, 让改动从临时状态变成正式记录; 06 加上分支和 Pull Request, 让你的工作可以和别人的并行而不打架; 07 则把日常用分支时那些具体会卡住的地方逐个扫掉.

有了地方干活, 干完的活留得下来, 花的钱心里有数. 这三样凑齐, 就是一个能独立开展工作的人的最小配置.

## 6. 一次完整的日常循环

把上面那条主线落到具体动作上, 一次典型的开发日大概是这个样子. 这份清单值得收藏, 卡住的时候回来对一遍, 通常就知道自己漏了哪一步.

1. 打开 Codespace, 先看一眼左下角状态栏, 确认自己在哪个分支.
2. 如果本地的 `main` 落后了, 先同步一次, 让它跟上 GitHub.
3. 从 `main` 创建一个新分支, 用 Create new branch from... 明确指定基础分支.
4. 在这个分支上写代码, 改文件.
5. 改到一个阶段就 stage, commit, 消息写清楚这次改了什么.
6. push 上去. 第一次推新分支时确认发布.
7. 在 GitHub 上开 Pull Request, 检查改动, 合并回 `main`.
8. 合并后删掉这个分支, 回到 Codespace 把 `main` 同步到最新.
9. 今天不做了就 Stop; 这个任务彻底结束了, 确认代码都已 push 之后就 Delete.

第 1 步和第 9 步最容易被跳过, 而它们恰恰是最省事的两步: 一个防止你改错地方, 一个防止你多花冤枉钱.

## 7. 云端环境是脚手架, 不是终点

开篇说过, 这门课是写给手上只有 Windows 电脑的人的. 现在可以把那个话题收掉了.

云端开发环境是一副很好的脚手架. 它让你在还没有趁手工具的时候就能开始正经干活, 而不是先花一个月和安装程序搏斗. 但脚手架的意义在于让房子能盖起来, 不在于永远立在那里. 如果哪天你换了一台 Mac, 或者给自己配好了一套顺手的本地环境, 该搬就搬, 不用觉得可惜.

搬家的成本比你想的低得多, 因为这门课教的东西几乎没有一样是 Codespaces 专有的. 本地版的 VS Code 界面和你现在用的几乎一模一样, 源代码管理面板在同一个位置, 分支菜单也在左下角同一块地方. GitHub Desktop 换了个外观, 但 stage, commit, push, branch, PR 还是那几件事. 你学到的是概念, 换工具只是换一套按钮的位置.

同时, 有一件事不会因为你换了电脑而改变: 需要做不确定的实验时, 开一个云端环境, 折腾完直接删掉, 依然是最省心的做法. 这个用途会一直跟着你.

## 8. 以后到底在哪干活

这门课教完了, 但有个很实际的问题没回答: 下次你要开始一个新任务, 是打开 Codespaces, 还是打开本地的编辑器?

没有一个统一答案, 取决于两件事: 你手上有什么机器, 以及这次要干的是什么活. 下面这张表基本覆盖了日常.

| 手上的机器 | 这次要干的活 | 在哪干 | 为什么 |
| :--- | :--- | :--- | :--- |
| 有 Mac | 严肃地学习或做项目 | 本地 | 本地版 VS Code 或 PyCharm 配上 GitHub Desktop, 响应快, 不耗额度, 也不依赖网络. 这是你的主场 |
| 有 Mac | 做实验 | Codespaces | 试没听过的工具, 跑来路不明的代码, 装一堆东西看看会怎样. 折腾完直接删掉, 你的 Mac 干干净净 |
| 只有 Windows | 写代码或跑数据 | Codespaces | 这就是这门课从头到尾在讲的那件事, 借一台 Linux 机器干活, 绕开本地环境的所有麻烦 |
| 都行 | 调研, 查资料, 写文档 | 本地桌面应用 | 纯文本的活儿不需要跑程序, 也就不需要开发环境, 用 AI 的桌面版更舒服, 比如 Claude Desktop, Codex, Antigravity |
| 只有 Windows | 让 AI 帮你做开发, 跑数据 | Codespaces 加 AI 的 CLI 版 | 桌面应用装在你的 Windows 上, 但真正干活的环境在云端, 让 AI 直接在那台 Linux 机器上操作文件, 跑命令, 装依赖 |

最后那一行的组合越来越常见, 它顺带回答了另一个问题: 这门课刻意避开了命令行, 但你一旦开始用 CLI 版的 AI 工具, 自然而然就会接触到它, 而那时候你已经有了概念基础, 学起来会轻松很多.

一句话概括: 严肃干活且机器趁手就用本地, 要冒险或者机器不趁手就上云端, 纯文本的活儿哪个顺手用哪个.

## 9. 如果还想往前走

这门课到这里就够用了, 但 Codespaces 还有两块内容是自然的下一站. 下面只给方向和入口, 不展开讲. 关键字复制进搜索引擎就能开始查, 话题那一句复制给 AI 就能往下深挖.

**一次性把环境配好, 让谁开都一样.** 这门课里你用的一直是 GitHub 给的默认环境. 但真实项目往往要特定的语言版本, 特定的依赖, 特定的编辑器插件, 而这些是可以写进仓库里的: 之后谁开这个仓库的 Codespace, 谁就自动拿到同一套配置, 一次都不用手动装. 说白了, 这是把 "在我电脑上能跑" 这个老问题连根拔掉的办法, 也是云端环境真正的杀手锏.

- 搜索关键字: `dev container`, `devcontainer.json`, `Codespaces prebuilds`
- 一句话话题: 我想给自己的仓库加一份 dev container 配置, 让任何人打开 Codespace 都自动拿到同样的语言版本, 依赖和插件, 请从零讲一遍.

**把云端跑起来的东西给别人看.** 迟早你会在 Codespace 里启动一个网站或者一个服务. 这时候会冒出一个本地开发根本不存在的问题: 程序跑在 GitHub 的服务器上, 不在你的电脑上, 那浏览器该开哪个地址, 别人能不能也打开看一眼, 要不要设成公开. 这一整套机制是云端环境独有的, 也是你把作品拿给别人看的通道.

- 搜索关键字: `Codespaces port forwarding`, `forwarded ports`, `port visibility public`
- 一句话话题: 我在 Codespaces 里跑起来一个开发服务器, 想搞清楚端口转发是怎么回事, 以及怎么把某个端口临时公开给别人访问.

## 10. 回顾

- 这门课的主线是三段: 有地方干活, 干完的活留得下来, 花的钱心里有数.
- 日常循环从确认分支开始, 到 Stop 或 Delete 结束, 第一步和最后一步最容易被跳过, 也最省事.
- 云端环境是脚手架, 有条件了就该换成本地环境, 但一次性实验这个用途会一直保留.
- 这门课教的是概念不是工具, 换到本地 VS Code 或 GitHub Desktop 几乎没有迁移成本.
- 该在哪干活取决于两件事: 机器趁不趁手, 以及这次的活儿是不是需要开发环境. 严肃干活且机器趁手就用本地, 要冒险或者机器不趁手就上云端, 纯文本的调研和写作用本地桌面应用更舒服.
- Windows 加上 AI 工具的命令行版本跑在 Codespaces 里, 是目前很实用的一种组合.
- 想继续往前走, 两个方向: 用 dev container 把环境配置写进仓库, 以及用端口转发把云端跑起来的服务给别人看.

## 11. 导师寄语

我想用一件和技术无关的事情来收尾.

这门课真正想给你的, 其实不是 Git 的用法. Git 只是一个例子. 你在这门课里反复做的那件事是: 先想清楚自己处在什么状态, 再动手. 改之前确认在哪个分支, 删之前确认代码推上去了, 花钱之前确认机器配置对不对. 这些动作单个看都很小, 但它们背后是同一个习惯.

绝大多数让人懊恼的错误, 都不是因为操作太难, 而是因为操作对了但对象错了. 在正确的分支上做了错误的事, 和在错误的分支上做了正确的事, 后者反而更难收拾. 这个道理在写代码之外一样成立.

另一件想说的是, 你在这门课里养成的那个 "反正搞坏了删掉重来" 的心态, 比任何一条具体知识都值钱. 学得快的人和学得慢的人, 差别常常不在智力, 而在敢不敢按下那个不确定的按钮. 有一个删掉重来毫无代价的环境, 你就敢试; 敢试, 反馈就来得快; 反馈快, 进步自然就快.

所以最后这句话是: 去找点东西折腾. 建一个仓库, 开一个分支, 写点什么, 推上去. 写得好不好没关系, 这门课教你的整套流程, 本来就是为了让你可以放心地写得不好.
