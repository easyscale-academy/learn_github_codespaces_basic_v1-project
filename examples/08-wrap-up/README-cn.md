# 收尾: 把这套工作流带走

## 1. 概览

到这里, 这门课的内容就全部讲完了.

前面每一篇解决的都是一个具体问题, 一篇一篇读下来, 你可能还没意识到它们合起来是什么. 这一篇不教新东西, 只做三件事: 把散落的知识点串成一条线, 说清楚云端环境在你整个学习路径里处于什么位置, 以及指出下一步最值得花力气的方向.

---

## 2. 学习目标

技能这个东西有个特点: 学的时候是一块一块学的, 用的时候却是连成一片用的. 如果只记住了一块块的操作, 遇到真实场景时还是会卡, 因为真实场景不会告诉你现在该用哪一块.

所以收尾这一步不是走形式. 把学过的东西重新组织成一条你能从头讲到尾的主线, 它才算真正变成你的.

读完这篇, 你将能够:

1. 用一条完整的主线复述这门课教过的全部内容
2. 说出一次完整的日常开发循环包含哪些步骤, 以及它们的先后顺序
3. 判断云端开发环境在什么时候是最优解, 什么时候该换成本地环境
4. 说清楚下一步该学什么, 以及为什么是它

## 5. 你会的其实是一条完整的主线

回头看, 这门课讲的是同一件事的六个阶段.

开头解决的是有没有地方干活的问题. 第一篇讲清楚了为什么会有环境这道门槛, 第二篇给了你一个绕过去的办法, 第三篇让你在那个环境里不再迷路. 到这里为止, 你有了一个能干活的地方.

中间三篇解决的是干完的活怎么留下来的问题, 这是这门课真正的重头. 第四篇教会你 commit 和 push, 也就是让改动从临时状态变成正式记录; 第五篇加上了分支和 Pull Request, 让你的工作可以和别人的并行而不打架; 第六篇则把日常用分支时那些具体会卡住的地方逐个扫掉.

最后一篇解决的是这件事花多少钱, 以及怎么管理才不浪费.

有了地方干活, 干完的活留得下来, 花的钱心里有数. 这三样凑齐, 就是一个能独立开展工作的人的最小配置.

---

## 6. 一次完整的日常循环

把上面那条主线落到具体动作上, 一次典型的开发日大概是这个样子. 这份清单值得收藏, 卡住的时候回来对一遍, 通常就知道自己漏了哪一步.

1. 打开 Codespace, 先看一眼左下角状态栏, 确认自己在哪个分支.
2. 如果本地的 `main` 落后了, 先同步一次, 让它跟上 GitHub.
3. 从 `main` 创建一个新分支, 用 Create new branch from... 明确指定基础分支.
4. 在这个分支上写代码, 改文件.
5. 改到一个阶段就 stage, commit, 消息写清楚这次改了什么.
6. push 上去. 第一次推新分支时确认发布.
7. 在 GitHub 上开 Pull Request, 检查改动, 合并回 `main`.
8. 合并后删掉这个分支, 回到 Codespace 把 `main` 同步到最新.
9. 今天不做了就 Stop; 这个任务彻底结束了, 确认代码都已 push 之后就 Delete.

第 1 步和第 9 步最容易被跳过, 而它们恰恰是最省事的两步: 一个防止你改错地方, 一个防止你多花冤枉钱.

---

## 7. 云端环境是脚手架, 不是终点

开篇说过, 这门课是写给手上只有 Windows 电脑的人的. 现在可以把那个话题收掉了.

云端开发环境是一副很好的脚手架. 它让你在还没有趁手工具的时候就能开始正经干活, 而不是先花一个月和安装程序搏斗. 但脚手架的意义在于让房子能盖起来, 不在于永远立在那里. 如果哪天你换了一台 Mac, 或者给自己配好了一套顺手的本地环境, 该搬就搬, 不用觉得可惜.

搬家的成本比你想的低得多, 因为这门课教的东西几乎没有一样是 Codespaces 专有的. 本地版的 VS Code 界面和你现在用的几乎一模一样, 源代码管理面板在同一个位置, 分支菜单也在左下角同一块地方. GitHub Desktop 换了个外观, 但 stage, commit, push, branch, PR 还是那几件事. 你学到的是概念, 换工具只是换一套按钮的位置.

同时, 有一件事不会因为你换了电脑而改变: 需要做不确定的实验时, 开一个云端环境, 折腾完直接删掉, 依然是最省心的做法. 这个用途会一直跟着你.

---

## 8. 下一步: 去学命令行

如果只能推荐一件事, 那就是命令行.

这门课刻意避开了它. 从头到尾你都在点按钮, 这是有意的安排: 一次只学一样东西, 先把概念搞懂, 工具可以慢一步. 现在概念你已经有了, 该轮到工具了.

值得学的原因很实际. 图形界面能覆盖的操作是有限的, 遇到稍微特殊一点的情况就没有对应的按钮, 而命令行没有这个上限. 而且熟练之后它明显更快, 这也是为什么大部分有经验的开发者最后都回到了命令行. 更重要的是, 网上绝大多数答案, 报错的解决办法, 别人给你的指令, 都是命令行形式的, 看不懂就等于把自己挡在了整个知识库外面.

好消息是, 你现在学它会比一开始就学轻松得多. `git branch`, `git checkout`, `git merge`, `git push` 这些命令做的事情, 和你这门课里点过的按钮完全一样. 概念已经在你脑子里了, 剩下的只是给每个概念配一个名字. 这跟从零开始完全是两回事.

除此之外还有两个方向可以考虑: 找一个真实的小项目, 把这套工作流完整用上一遍, 哪怕项目本身很小; 或者去了解一下 GitHub 上的协作细节, 比如怎么审查别人的 PR, 怎么处理合并冲突. 但这两件事都可以等, 命令行不用等.

---

## 9. 回顾

- 这门课的主线是三段: 有地方干活, 干完的活留得下来, 花的钱心里有数.
- 日常循环从确认分支开始, 到 Stop 或 Delete 结束, 第一步和最后一步最容易被跳过, 也最省事.
- 云端环境是脚手架, 有条件了就该换成本地环境, 但一次性实验这个用途会一直保留.
- 这门课教的是概念不是工具, 换到本地 VS Code 或 GitHub Desktop 几乎没有迁移成本.
- 下一步最值得投入的是命令行, 而且现在学比一开始学容易得多.

## 10. 导师寄语

我想用一件和技术无关的事情来收尾.

这门课真正想给你的, 其实不是 Git 的用法. Git 只是一个例子. 你在这门课里反复做的那件事是: 先想清楚自己处在什么状态, 再动手. 改之前确认在哪个分支, 删之前确认代码推上去了, 花钱之前确认机器配置对不对. 这些动作单个看都很小, 但它们背后是同一个习惯.

绝大多数让人懊恼的错误, 都不是因为操作太难, 而是因为操作对了但对象错了. 在正确的分支上做了错误的事, 和在错误的分支上做了正确的事, 后者反而更难收拾. 这个道理在写代码之外一样成立.

另一件想说的是, 你在这门课里养成的那个 "反正搞坏了删掉重来" 的心态, 比任何一条具体知识都值钱. 学得快的人和学得慢的人, 差别常常不在智力, 而在敢不敢按下那个不确定的按钮. 有一个删掉重来毫无代价的环境, 你就敢试; 敢试, 反馈就来得快; 反馈快, 进步自然就快.

所以最后这句话是: 去找点东西折腾. 建一个仓库, 开一个分支, 写点什么, 推上去. 写得好不好没关系, 这门课教你的整套流程, 本来就是为了让你可以放心地写得不好.
