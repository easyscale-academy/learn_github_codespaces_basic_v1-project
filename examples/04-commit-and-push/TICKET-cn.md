# 完成一次 Commit 和 Push 循环

## 1. 目标

先读完关于在 Codespaces 中修改文件并推送到 GitHub 的教程, 理解 Edit, Stage, Commit, Push 各自做什么, 以及 Stage 和 Commit 为什么是两个独立步骤. 然后在自己名下的仓库里, 亲手走一遍完整的 Edit 到 Stage 到 Commit 到 Push 循环, 并在 GitHub 上确认改动真的生效了. 这样做的意义在于, 只有走通这条链路, 你在 Codespaces 里做的改动才真正被保存下来, 变成项目历史的一部分, 而不是留在某个随时可能被删除的临时环境里.

---

## 2. 要做的事情

1. 完整读一遍教程, 确认自己理解 Stage, Commit, Push 三者分别做什么, 以及它们之间的区别.
2. 打开一个属于你自己的仓库, 启动一个 Codespace.
3. 编辑一个文件: 如果仓库里有 `README.md`, 就修改它, 比如加一行文字; 如果没有, 就新建一个文件.
4. 保存文件后, 留意文件名变成橘黄色, 并出现 `M` 标记.
5. 打开源代码管理面板 (左侧活动栏里像树枝分叉的图标), 把改动 Stage 起来.
6. 在 Message 输入框里写一条简短的 commit 消息, 然后点击 Commit 按钮完成提交. 如果 Commit 按钮是灰的, 说明你还没有 Stage 任何文件, 或者消息框还是空的.
7. 点击 Sync Changes, 或者点击状态栏的上箭头, 把本地的 commit 推送到 GitHub.
8. 刷新 GitHub 上对应仓库的页面, 确认改动确实出现在那里; 如果没看到变化, 试试强制刷新 (Windows 或 Linux 上是 `Ctrl+Shift+R`, Mac 上是 `Cmd+Shift+R`), 或者稍等几秒再试一次.
9. 记下你这个仓库的地址, 格式类似 `https://github.com/your-username/your-repo-name`, 用于后续验收展示. 如果你名下暂时没有任何仓库, 先在 GitHub 上新建一个再开始.

**预计用时:** 15 到 20 分钟

---

## 3. 检查清单

- [ ] **理解 Stage 与 Commit 的区别**: 能用自己的话说清楚 Stage 是选择要提交什么, Commit 是把选中的改动正式记录进本地历史, 两者为什么要分开.
- [ ] **能识别修改文件后的视觉提示**: 知道文件被修改后文件名会变成橘黄色, 并带上 `M` 标记, 分支名后面会出现星号.
- [ ] **完成一次 Stage 到 Commit 到 Push 的完整流程**: 在自己的仓库里独立走完全部步骤, 没有卡在中间任何一步.
- [ ] **确认改动真的到达 GitHub**: 刷新仓库页面后, 能看到自己刚才做的改动, 而不是只停留在本地的 Codespace 里.
- [ ] **准备好可验收的仓库链接**: 手上有一个可以直接打开验证的仓库 URL, 里面包含这次的改动记录.
